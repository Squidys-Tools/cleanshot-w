# OCR engine evaluation

## Verdict

**Decision (2026-10-15): Adopt Tesseract as the port's OCR engine.** Its speed
and word-level confidence scores win; the one-character error on the settings
fixture is acceptable. Windows.Media.Ocr remains in the evaluation crate as a
Windows-only comparison; it was exact on these fixtures but does not expose
confidence scores.

`cleanshot-ocr` defaults to Tesseract on every platform. On Windows, pass
`--engine winrt` to run the comparison. The Windows CI workflow runs both
engines on the same generated PNG fixtures, prints character/word error rates
and per-process elapsed time, and uploads the report with both CLI builds and
the English fallback model.

## Samples and measurements

The three small fixtures are generated by `samples/generate_samples.py` with
DejaVu Sans: clean text, a settings-like line with punctuation and mixed case,
and blurred low-contrast text. Ground truth is in `samples/ground-truth.txt`.
The evaluator normalizes whitespace, then computes character error rate (CER)
and word error rate (WER) with edit distance. These are synthetic samples, not
a representative product benchmark.

The Linux table is one Tesseract run on the current cloud runner. The Windows
table is one `windows-2025` CI run; the same values are in
`evaluation-windows.txt` in the downloadable artifact. Every timing includes a
fresh process and OCR-engine initialization, so these are observations rather
than latency distributions or steady-state measurements.

**Linux Tesseract baseline**

| Sample | Tesseract exact | CER | WER | Confidence | Elapsed |
| --- | --- | ---: | ---: | ---: | ---: |
| `clean-lines.png` | Yes | 0.0% | 0.0% | 93% | 290 ms |
| `settings-text.png` | No (`DPI` → `DPl`) | 2.4% | 14.3% | 94% | 237 ms |
| `low-contrast.png` | Yes | 0.0% | 0.0% | 95% | 185 ms |

**Windows-2025 paired-engine results**

| Sample | WinRT CER/WER | WinRT confidence | WinRT elapsed | Tesseract CER/WER | Tesseract confidence | Tesseract elapsed |
| --- | --- | --- | ---: | --- | ---: | ---: |
| `clean-lines.png` | 0.0% / 0.0% | Not exposed | 286 ms | 0.0% / 0.0% | 94% | 69 ms |
| `settings-text.png` | 0.0% / 0.0% | Not exposed | 119 ms | 2.4% / 14.3% | 94% | 65 ms |
| `low-contrast.png` | 0.0% / 0.0% | Not exposed | 90 ms | 0.0% / 0.0% | 96% | 71 ms |

On these three synthetic samples, WinRT was exact after whitespace
normalization; Tesseract made one character error on `DPI-aware`. Tesseract was
faster in this single run and supplied confidence. The decision is to accept
that fixture error in favor of speed and confidence; the sample set is too
small to make a general accuracy claim.

The Linux Tesseract CLI release binary measured **560,440 bytes**. On Windows,
the WinRT-only CLI measured **260,096 bytes**, while the combined
WinRT+Tesseract CLI measured **7,680,000 bytes**: Tesseract adds **7,419,904
bytes** to the executable. The separate English `eng.traineddata` file measured
**4,113,088 bytes**. WinRT uses installed Windows language resources instead
of bundling a model.

## Language support and licensing

Windows.Media.Ocr recognizes languages installed and available to the Windows
user profile. The CLI accepts a Windows language tag such as `en-US`; it does
not install language packs. Tesseract accepts traineddata language codes such
as `eng`, and supports additional languages by supplying their traineddata
files with `--tessdata-dir`. The artifact bundles only the English fast model.

The `windows` bindings are MIT/Apache-2.0 and call the Windows OCR runtime. The
Tesseract engine is Apache-2.0, `leptess` is MIT, Leptonica is BSD-2-Clause,
and the bundled fast English traineddata is Apache-2.0. Tesseract is a real
native dependency: Linux builds require Tesseract, Leptonica, and Clang; the
Windows workflow installs its static libraries through vcpkg. The Windows
artifact contains the model separately from the executable.

## Limits

The Linux baseline cannot execute Windows.Media.Ocr, and the Windows CI run is
not a substitute for checking the app on a target Windows machine. Verify
window capture, cursor inclusion/exclusion, mixed-DPI behavior, and startup
registration on that machine before adopting the port path.
